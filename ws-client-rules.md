# WebSocket client rules

The wire contract is [`asyncapi.yaml`](asyncapi.yaml), generated by `tools/build.py` from the
AsyncAPI document the server publishes at `https://api.cexy.io/api/v1/asyncapi.json`. This file
holds the rules an SDK client follows on top of it: snapshots, resynchronisation, sequences and
sign-outs. The shared client cases in `conformance/ws/` test these rules. Where this file and
`asyncapi.yaml` disagree, `asyncapi.yaml` is authoritative: open an issue so this file is fixed.

## Rules

One multiplexed connection carries every subscription.

Client rules (all are required for a correct client):
- Send `{"op":"ping"}` at least every 30 s. Only client frames reset the server's idle
  timer; an idle connection is closed after 90 s (checked every 30 s, so 90-120 s).
- Accept unsolicited `{"type":"pong"}` frames (no id) every 30 s.
- Order books: subscribe first, then GET /api/v1/markets/{symbol}/orderbook (sequence S),
  drop updates with sequence <= S; every update replaces the top 50 levels in full.
  A sequence gap marks the book stale until the next update. Sequences reset when the
  server restarts: take a fresh snapshot after every reconnect. Never merge REST levels
  deeper than 50 into WebSocket state.
- `CONCURRENT_MODIFICATION` error frames (null id, no channel) mean messages were
  dropped: resynchronise all books and channels.
- Limits: 240 client messages per minute (fixed window, pings count; exceeding it closes
  the socket), 100 subscriptions (extra channels in a batch are refused without closing),
  64 KiB per message, channel names up to 64 characters, text frames only.
- Subscriptions are not restored after a reconnect: re-authenticate, re-subscribe and
  resynchronise. Use exponential backoff with jitter.
- Private channels need `auth` with a session access token, or `auth_key` with an API key
  (sign the welcome's single-use challenge; see conformance/signing).
- Every client request that carries an `id` is acknowledged with that `id`:
  `authenticated`, `subscribed`, `unsubscribed`, `pong` or `error`.

Futures channels (server 6919535; binding client rules in conformance/ws/futures.json):
public `futures.mids`, `futures.orderbook:{coin}`, `futures.trades:{coin}`,
`futures.candles:{coin}:{interval}` (1m 5m 15m 1h 4h 1d), `futures.status`; private
`futures.account` (events `futures.positions` and `futures.orders`, full state, sent on
subscribe and on change). The coin is case-sensitive, exactly as GET /api/v1/futures/markets
lists it. Public futures channels send no snapshot on subscribe (seed from REST); book
levels are `{price, size}` objects and every book frame is complete. `futures.resync`
(`data: {}`) means data on that channel may have been missed: refetch over REST; on
`futures.account` the server's poller has stopped, so unsubscribe and subscribe again.
Error frames carry no `details`: back off yourself after `RATE_LIMITED`. A 17th live
account in one api process is refused `RATE_LIMITED`; REST reads still work.

Private subscriptions (orders, balances, deposits, withdrawals, account) belong to the account
the connection is authenticated as at that moment. They end in three cases.
(1) An `auth` frame succeeds for a different account: the `authenticated` reply names the new
user_id, and every private subscription made for the previous account has already ended.
Authenticating again as the same account, for example with a refreshed token, keeps them.
(2) An `auth` frame fails for any reason: the error reply is sent, and the connection is no
longer authenticated; private subscribe requests are refused until an `auth` succeeds.
(3) The session this connection authenticated with is revoked: the `session.revoked` event with
`current: true` is delivered on the `account` channel first, then `signed_out` with reason
`revoked`, and the connection is no longer authenticated, as in (2). Treat the pair as one
sign-out: the second frame of it changes nothing. A revocation of another session of the same account
(`current: false`) changes nothing. Public subscriptions are never affected. After (1),
re-subscribe the private channels you need; after (2) or (3), authenticate and then
re-subscribe. An `UNAUTHENTICATED` error carrying a subscribe request's id is a refused
subscribe, not a sign-out. Shared client cases: conformance/ws/private_signout.json.

Private event sequences. Every private event frame (orders, balances, deposits, withdrawals,
account) carries a frame `sequence` per topic: one account and one channel on one server
instance, shared by that account's sockets there. It starts at 1 when the topic is created
and restarts at 1 after a server restart, or when the account's last socket on the instance
leaves the channel and the topic is created again. A socket that joins an existing topic
starts mid-count. Judge gaps only between frames received on the same connection, and take
the first frame after `subscribed` as the baseline. Channels with more than one publisher
(orders: one per market; account) can swap two adjacent frames within a moment. A lower
number than expected is late, not lost, and a higher number should be given a short reorder
window (about 250 ms) to fill in before it is treated as a gap. `balances` has a single
publisher.

Live balances. `balance.updated` data carries the balance's own `sequence` (the same value as
`sequence` on GET /api/v1/account/balances rows). It never decreases, but it can skip values or
repeat, because two quick writes can be delivered as two events carrying the later state. A
skip is not a loss. To keep balances live: subscribe to `balances`, wait for `subscribed`,
then fetch GET /api/v1/account/balances as the snapshot. Apply an event only when its
`data.sequence` is greater than the stored sequence for that asset (an equal value is a
duplicate). Fetch a new snapshot on a frame-sequence gap, on `balances.resync`, on a
`CONCURRENT_MODIFICATION` error with a null id, and after every reconnect; keep applying
newer events after it. Never refetch because `data.sequence` skipped values. `balances.resync`
(data `{}`, no frame sequence) means the server could not resume its change stream and events
may be missing. Shared client cases: conformance/ws/live_balances.json and
conformance/ws/private_sequence_gap.json.

Currently, the `deposits` and `withdrawals` channels carry only changes made through the API (a
withdrawal requested, cancelled, approved, rejected or released). A deposit being credited, or
a withdrawal being broadcast or confirmed on chain, produces no frame on those channels; poll
the REST lists for those states. The balance change itself arrives on `balances`. A planned
server update adds those changes (one publisher per topic) and the `deposits.resync` /
`withdrawals.resync` events (data `{}`, no frame sequence), meaning "refetch that list".

Order closes. An order can end without executing in full, and the `orders` channel then sends
`order.updated` (status `rejected`) or `order.cancelled`, with `status_reason` saying why (free
text; new reasons may appear, so display it rather than parse it). Some of these the exchange
closes on its own; others are ordinary outcomes of the order itself (a post-only order that
would have crossed, a fill-or-kill that could not fill, an IOC or market order that ran out of
liquidity, a self-trade block). A reason other than `Cancelled by the account holder` does not
by itself mean the exchange closed the order. A placement can answer 2xx with status `rejected`
or `cancelled`: that answer is final, fills in it stand, and the order must not be placed again
automatically. A triggered stop has no HTTP answer, so the `orders` channel (or a refetch) is
the only place its outcome appears; once triggered it carries its triggered `type` (`market` or
`limit`), so recognise it by `triggered_at` or `stop_price`. The server sends each close at
most once (a frame can be lost if the server fails just after the close), and a client can see
the same close several times: in the HTTP answer to its own request, on the `orders` channel,
and in a REST refetch after a gap or a reconnect. Act on a close once per (order id, status); a
later frame with a different status for the same order id is a new event. A notification of
kind `order_closed` may also arrive for some closes.

Server sign-out. `{"type":"signed_out","reason":...}` (no id,
channel or sequence) is sent when this connection's access token expired more than 30 s ago
without a new `auth`, or when a periodic check finds its session revoked. Private
subscriptions are gone; public subscriptions and the socket stay, and a fresh `auth` on the same
socket is accepted (then re-subscribe the private channels). The reason set may grow: treat any
value as a sign-out. Re-send `auth` on every token refresh: that keeps the subscriptions and
resets the expiry timer. Shared client cases: conformance/ws/server_signout.json.

## Channels

Public: ticker, ticker:{market}, orderbook:{market}, trades:{market}, markets,
futures.mids, futures.orderbook:{coin}, futures.trades:{coin},
futures.candles:{coin}:{interval}, futures.status.
Private (auth required): orders, balances, deposits, withdrawals, account,
futures.account.
`account` carries only session.revoked. With `current: true` it means "authentication
lost" (private subscriptions end); with `current: false` nothing changes. The server does
not close the socket.

## Frame notes

- `welcome.protocol_version`: Increments only on breaking changes; warn on unknown values and continue.
- `welcome.heartbeat_interval_seconds`: The server's pong cadence (30), not a client deadline.
- `auth.token`: Session access token. Never put credentials in the URL.
- `pong`: Reply to a client ping (echoes its id), or an unsolicited server pong every 30 s (no id).
- `authenticated`: Acknowledges a successful `auth` request; echoes its id. `user_id` is always present.
- `subscribed`: Echoes the request id and lists every channel the request now holds, including ones already held. Not sent when every channel in the request was refused.
- `error.code`: Same vocabulary as REST error.code (errors.yaml). Echoes the request id when caused by a request. CONCURRENT_MODIFICATION with a null id means this socket read too slowly and the server dropped events for one of its topics (the message says how many); the connection and subscriptions stay open. It names no channel: fetch fresh snapshots of everything you keep.
- Event `type`: Ignore unknown event types (additive changes do not bump protocol_version).
- Event `sequence`: Public channels: per channel, +1 per update, resets on server restart. Private channels: per topic (see the description above). balances.resync has none.
- Event `data`: Amounts are decimal strings. orderbook.update data is {symbol, full: true, bids, asks}: always the complete top 50 of both sides, replacing the previous state (there are no deltas).
